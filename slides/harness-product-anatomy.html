From Prompt to Product · 学习笔记

一句话需求，
如何变成一个交付的项目

我在 Coze 上编排工作流、发布成 API、集成进网站；也在 Claude Code 里只提一个需求， 就看着 agent 交付出完整项目。这篇文章回答两个问题：这类产品凭什么能做到？底层的代码逻辑是什么？

入口 Coze 工作流 → API → 网站 对照 豆包 / ChatGPT 为什么不行 拆解 harness 架构图 原理 亲手实现的代码逻辑
01 · 亲历 — 两类产品，同一件事

我先把需求跑通了三遍

同一个目标——把数据做成一个能看的网站——我用三种越来越「自动化」的方式各做了一遍：

①
Coze 工作流可视化编排

在 Coze 画布上把 LLM 节点 / 代码节点 / 插件 拖成一张 DAG：输入数据 → 模型加工 → 输出结构化结果，发布成工作流 API。编排逻辑写在画布上——每一步做什么，是我（人）决定的。

②
API 集成进网站沙盒 + code agent 开发

把工作流 API 接入 Coze 沙盒环境，与 code agent 开发好的网站拼装，实现数据展示。此时模型在「节点里」干活，网站在「沙盒里」跑——能力有了，但胶水还是我写的。

③
Claude Code 一句话交付agent harness

日常用 Claude Code：我只给一个需求，agent 自己读代码、改文件、跑命令、修报错，交付一个成熟项目。编排逻辑消失了——不是没有了，是搬进了模型的工作过程里。

三种形态背后是同一类产品：把「一次文本生成」包装成「能连续干活并交付」的系统——业界叫它 Agent Harness。 区别只在「谁做路由」：①人拖节点 ②人写胶水 ③模型自己在上下文里决策。
02 · 拆解 — Harness 产品架构图

模型只做决策，其余都是 harness

一个 harness 产品的完整纵切面（Claude Code / Coze agent / 我手撕的 pi-from-scratch 都长这样）：

用户一句话需求
「帮我把这批数据做成一个展示网站」——需求可以只有一句，完整性由 harness 的循环来补。
↓提交给
界面层产品的外壳
TUI（Claude Code 终端） IDE 插件 Coze 画布（工作流编辑器） Coze 沙盒（预览网站） Web 对话框
外壳千差万别，往下都是同一套 harness。
↓进入核心
HARNESS
模型之外的一切 —— 产品真正的工程重心
Agent Loop循环 · 灵魂

while 循环：流式调用 → 有 tool_call 就执行 → 结果回填上下文 → 继续，直到模型不再调工具。四种停止条件 + abort 兜底。

上下文管理预算

token 估算、安全切点、超限摘要压缩；skills 目录常驻 + 按需加载（渐进披露）——上下文是有限资源。

工具系统双手

每个工具带 schema 契约：校验失败返回结构化错误让模型自纠；并行执行 + 超时兜底。工具是模型唯一的动作形式。

安全护栏信任

执行前审批、敏感路径拦截、结果脱敏、死循环检测——能干活的系统必须有闸门。

生态插座能力的来源
内置工具：read / write / bash / grep … MCP：JSON-RPC 接外部工具服务 Skills：目录 + load_skill 按需加载工作流知识 Coze 工作流 API：也是一种「外部能力」
↓ ↑tool_call 发出 / tool_result 喂回 —— 循环的血肉
LLM Provider决策引擎
SSE 流式返回四类事件：text_delta / tool_call / done / error。模型永远只做一件事：决定下一步。
执行环境手脚所在
文件系统终端命令沙盒（Coze / 本地）外部 API
确定性代码在这里跑，结果作为「感知」回传。
↓循环收敛后
交付可运行的产物
一个能跑的项目（代码 + 文档 + 测试）数据展示网站工作流 API

对照我的三遍经历：Coze 把「循环」外化成画布上的 DAG（路由写给人看）， Claude Code 把循环藏在 harness 里（路由由模型在上下文中决策）。模型越强，路由越多地从人搬到模型——这正是两种产品形态的分水岭。

03 · 提问 — 凭什么它能做到？

同样的模型，为什么豆包 / ChatGPT 不行

先澄清：豆包、ChatGPT 和 Claude Code 背后是同级别的模型。差别不在模型，在产品把模型「包」成了什么：

维度聊天 AI（豆包 / ChatGPT 对话框）Harness 产品（Claude Code / Coze agent）
交互形态✗ 一问一答，答完即止✓ 循环直到任务完成（while + 停止条件）
行动能力✗ 只能生成文本，文本不是动作✓ tool_call 执行真实动作：读写文件、跑命令、调 API
环境访问✗ 无文件系统 / 终端 / 沙盒✓ 工具连着真实环境，能创建项目并跑起来
上下文✗ 单会话窗口，长了就忘✓ 预算经营：压缩 / 笔记 / 按需加载，跨压缩保持连贯
状态持久✗ 关掉即失，重开靠用户复述✓ session 落盘、配对校验，崩溃可恢复
确定性✗ 全靠 token 生成，排序都可能出错✓ 确定性逻辑交给工具里的代码，模型只做路由
安全闸门— 不执行，所以不需要✓ 审批 / 拦截 / 脱敏 / 防循环——能干活才需要护栏
答案一句话：模型没变，变的是外面那圈工程——把「一次生成」包进「循环 + 工具 + 预算 + 护栏」，模型就从聊天框变成了能交付项目的 agent。 理论出处：ReAct（2022）证明「推理 × 行动」交错优于纯生成；harness 是这个闭环的工程化。
04 · 学习成果 — 底层代码逻辑与原理

我把它从零手撕了一遍

以下代码全部来自我的学习项目 pi-from-scratch（从零实现的极简 coding agent）。 四个模块，就是上面那张架构图的可运行注脚：

①
Agent Loopwhile 循环 · ~200 行的灵魂

「一句话交付项目」的全部秘密：模型决定下一步，harness 执行并回填，循环直到收敛。

while (true) {
  const events = await streamFn(model, context, tools)      // ① 流式调用：SSE 四事件
  if (stopReason === 'end_turn') break                        // ② 停止条件（四种之一）
  for (const call of toolCalls) {                            // ③ 工具 = 模型唯一的动作形式
    const result = await executeTool(call)                   //    校验 → 审批 → 超时兜底
    context.messages.push(toolResult(call, result))           // ④ 回填：必须与 call 配对！
  }
  if (estimateTokens(context) > 0.8 * window)                // ⑤ 预算检查
    await compactContext(context, streamFn)                 //    摘要压缩（失败保留原文）
}

停止条件有四条：end_turn（正常收工）/ max_tokens（截断）/ aborted（用户中断——为被跳过的调用补 error 结果，保配对）/ error（重试退避后仍失败）。

失败不抛异常：错误编码进事件流（error 事件），上层统一处理——循环永不因工具失败而崩溃。

这就是「边界比循环重要」：聊天 AI 缺的不是这个 while，是整个可安全回填的环境。

②
消息模型与配对安全为什么 session 恢复后不炸

模型看到的是一串消息；每个 tool_call 必须有对应的 tool_result，否则 API 直接 400。

[
  { role: 'user',      content: "把数据做成网站" },
  { role: 'assistant', tool_calls: [{ id: 'call_1', name: 'write_file', args: {...} }] },
  { role: 'tool',       tool_call_id: 'call_1',                        // ← 必须回指 call_1
                 content: "written: index.html (2.1 KB)" },
  { role: 'assistant', content: "已创建页面，接下来启动预览…" }   // 循环继续
]

三条纪律：abort 时丢弃未完成的 tool_calls 并补 error 结果；session.jsonl 逐行容错（崩溃可能写出半行 JSON，跳过单行好过丢全部历史）；压缩选点不能切在配对中间。

聊天 AI 没有「动作」，自然没有配对问题——整个消息模型就是为「行动」设计的。

③
上下文即预算长任务不失忆的原理

模型有 context rot（token 越多召回越差），所以上下文要像预算一样经营——工程原则：「最小的高信号 token 集」。

// 估算：chars / 4 近似 token，误差由 0.8 阈值的提前量吸收
const used = estimateTokens(context)
if (used > 0.8 * contextWindow) {
  const summary = await summarize(oldMessages)        // 让 LLM 自己摘要旧消息
  context.messages = [ summaryMsg(summary), ...recent ]  // 保留 system + 摘要 + 最近对话
}
// 两条红线：失败保留原文（空摘要比没有更危险）；abort 时不压缩

三板斧各管一摊：压缩管叙事连贯、笔记管任务状态（todo_write）、子代理管注意力分配。

Skills 渐进披露也是预算问题：目录（name + description）常驻只花几十 token，正文 load_skill 用到才进上下文。

④
能力插座MCP + Skills：能力从哪来

Coze 里我拖插件节点；harness 里对应两套协议——MCP 管连接，Skills 管工作流知识。

// MCP：stdio 上的 JSON-RPC 三步
send({ method: 'initialize', params: { protocolVersion: '2024-11-05' } })   // 握手
const { tools } = await request('tools/list')                          // 发现
await request('tools/call', { name, arguments })                     // 调用 → 适配成普通 AgentTool

// Skills：目录常驻 system prompt，模型自主路由后按需加载
"<available_skills> code-review: 审查代码并给出行级意见 …</available_skills>"
模型: load_skill({ name: 'code-review' })  →  "<skill_content> 完整指令 …</skill_content>"

防幻觉引导：「目录只有摘要，未加载前不要推断指令」——一句话挡住从摘要脑补工作流。

我亲测的迭代：关键词匹配激活（v1）漏激活、枚举不完、逐轮淡出；改模型语义路由（v2）后三个问题同时消失——路由本来就该交给模型。

回到最初的问题

Coze 让我把工作流「画」出来，Claude Code 让我把工作流「说」出来—— 两者中间隔着的，就是 harness：一个循环（模型决策）+ 一份预算（上下文经营）+ 一双手（工具）+ 一个插座（生态）+ 一套闸门（安全）。 聊天 AI 与 agent 的差距不在模型，在这圈工程——而它每一块都可以被亲手写出来、读懂、改进。这正是我这段时间的学习成果。
