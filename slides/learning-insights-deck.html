ACT 1 · 引子 · 一条真实的执行轨迹

一句话进，一份 docx 出——中间发生了什么？

❯ 用户输入请你根据本项目的实际情况来生成测试用例，并一一进行测试，并把最终测试结果以 docx 文件的形式存放在本目录下
轮 1
摸清「实际情况」感知回填

模型先调 read / glob：读 package.json、AGENTS.md、src/ 九个模块、已有 100 个用例——工具结果喂回上下文，「项目实况」在上下文里长出来。

轮 2
定用例清单待办整表替换

对照模块职责列清单：token 估算边界、切点三规则、配对安全、skills 匹配、审批拦截……写入待办工具，计划贴在上下文尾部。

轮 3+
写一个、跑一个错误是信号 · 超时兜底

write 新测试文件 → bash 跑 npm test（vitest run）→ 失败输出作为结构化错误回填 → 模型自纠再跑，直到全绿。

中途
上下文到 80%压缩红线

轮次一多预算吃紧：旧轮次压成一段摘要，任务与清单不丢；压缩失败则保留原文，绝不带病替换。

过闸
生成 docx 之前四道防线

要写脚本、跑命令：先审批放行；敏感路径直接拦截并告知原因；输出里的密钥形态打码后才进上下文。

交付
报告落盘停止条件 · 逐轮落账

write 生成脚本 → bash 运行 → 测试结果 .docx 出现在本目录 → 模型判定任务完成，循环停止——全程每轮已写进会话日志。

你只说了一句话——中间几十轮「读 · 写 · 跑 · 错 · 改 · 压 · 记」，是 harness 在替你转。 这六行里的每一个机制，后面的页都有一页专门讲它——整个 deck 就是这条轨迹的展开。
ACT 1 · 起点

一个问题，把我带进了 harness

场景一Coze 平台

拖拽搭工作流 → 发布 → 把工作流 API 集成到沙盒与 code agent 开发的网站里做数据展示。平台把「能跑」给了我，但里面是什么，完全黑盒。

场景二Claude Code

日常只说一句话的需求，agent 通过一系列 harness 工程直接交付一个成熟项目——读文件、改代码、跑测试、自己修错。

场景三豆包 / ChatGPT

同样一代大模型的聊天界面：能说，不能做。给不了文件系统，跑不了命令，交付不了项目。

疑问差距到底在哪？

三个场景用的可能是同一家实验室的模型——差距显然不在模型，在模型外面那层工程。那层工程叫 harness，我决定从零手撕一个看清它。

同一个模型，三种外壳——差距不在 LLM，在外壳；harness 把「①的对话」和「②的执行」组合起来，还加上了自适应的循环。
同一个时代的大模型，为什么有的只能聊天，有的能交付项目？ 这个问题就是全部的起点——后面的一切，都是在回答它。
ACT 2 · 方法（上）

我怎么学：三步循环，而不是看教程

STEP 1
调研先行

动手前先读 12 篇论文与工程报告（ReAct、Voyager、SWE-agent、Anthropic 工程指南…），把业界共识定成「应然」——不带偏见地动手，每写一个功能都知道它在文献里对应什么。

STEP 2
亲手实现

没有教程可抄——每个功能先自己想方案、再写代码、最后补单测。9 个模块 ~1,800 行，100 个测试全绿。别人的代码看十遍，不如自己的代码跑一遍。

STEP 3
精读对照

拿自己的实现去对照两个真实项目：pi（完整版目标形态）与 deepseek-harness（生产级制度），整理 19 条源码答疑——校验自己的取舍，也看清差距。

▸

参考真实项目，而不是参考教程——教程教的是「怎么做」，真实项目回答的是「为什么这么做、不这么做会死在哪」。

▸

小步快跑：按 P1 上下文 → P2 工具 → P3 工程地基 → P5 生态的顺序，每个阶段都是能跑、能测、能演示的完整状态。

12 篇 文献定共识 ~1,800 行 亲手实现 2 个 生产项目精读 原则 可读性优先于抽象，核心循环一屏读完

01

ACT 2 · 方法（延伸）· 精读开源代码库

三个代码库，三种读法

精读 · 制度deepseek-harness

DeepSeek 官方的生产级插件式 harness，我带着 19 个架构问题逐条追问：压缩管线（头锚定 + 尾部保留 + tool 配对完整才切）、剪枝（超长结果只留头 4096 尾 1024）、session / surface（log 唯一权威）、skills、plan、subagent / workflow。

最打动我：摘要不比原文短，就拒绝压缩——教科书不会写的防御细节。

对照 · 目标形态pi

教学版就是从它做减法。9 处源码对照入日志：两层重试（按状态码 / 错误消息分类）、停止回调、ToolResultMessage 独立 role、Anthropic 协议转换、StreamFn 注入、skills 纯指令渐进披露。

ACT 3 · 转变 1 / 4

模型能力 → 工程能力

以前我以为

产品强不强，取决于模型聪不聪明；prompt 写得好就是核心竞争力；换个更新的模型，一切问题都会消失。

现在我知道

同一个模型，裸 API 只能聊天；装进 循环 + 工具 + 上下文管理就能交付项目。Anthropic 的定义一针见血：「agent = 在循环中自主使用工具的 LLM」——重心全在工程那半句。

▸

自己的印证：我 318 行的核心模块里没有一行「智能」——全是 while 循环、消息配对、token 预算、超时兜底。智能全部来自模型，价值大量来自工程。

▸

工程决定下限也决定上限：死循环检测、失败不炸循环、恢复不报 400——模型再聪明，没有这些制度也跑不完一个真实任务。

文献印证 ReAct 2022 · Anthropic Building Effective Agents 代码印证 src/agent.ts —— 一个 while 循环是整个项目的灵魂
ACT 3 · 转变 2 / 4

上下文：容器 → 预算

以前我以为

上下文就是聊天记录，越大越好、塞满为止；模型「记得」所有说过的话；超窗了是大模型的锅。

现在我知道

上下文是稀缺资源，要像预算一样经营：token 越多注意力越稀（context rot），目标是「最小的高信号集合」——每个 token 都要挣自己的位置。

▸

经营手段是一套制度：用量到 80% 提前动手（绝不打满）→ 找安全切点（消息边界、不切工具配对、整轮对齐）→ 摘要替换（有损，所以失败时保留原文）。

▸

预算思维甚至管到缓存：deepseek 的前缀纪律——固定段落顺序、工具 schema 稳定——让摘要请求复用 KV 缓存，省上下文也是省钱的工程。

▸

自己的印证：压缩模块 14 个单测全在打边界——切点切错一处，会话恢复直接被 API 拒绝。

窗口是预算：system 常驻，旧对话可被摘要替换，到 80% 就动手，绝不打满。
文献印证 Anthropic Context Engineering 代码印证 context-management.ts · deepseek prune 8192
ACT 3 · 转变 3 / 4

错误：异常 → 信号

以前我以为

出错等于失败：抛异常、崩掉、给人看堆栈；错误越多说明程序越烂，目标是消灭错误。

现在我知道

在 agent 里，错误是喂回模型的信号：结构化地说清「哪个字段、什么问题、怎么错的」，模型下一轮自己纠正——大多数错误在循环内部就被消化了。

▸

失败不炸循环：工具错误、网络错误一律编码进事件流的 error 通道，循环永不因异常崩溃；限流与服务器错误做指数退避重试。

▸

「卡住」也是错误的一种：每个工具带超时（读 10s / 搜 15s / 命令 30s），连续三次同指纹调用判定死循环强制停下——失控被制度接管，而不是靠运气。

▸

SWE-agent 的印证：好的接口把错误信息设计成模型可读的反馈，agent 的自纠率是设计出来的，不是碰出来的。

错误走回路，不走异常——它是循环里信息量最大的那种输入。
文献印证 SWE-agent ACI：护栏 + 反馈 代码印证 四事件流 error 通道 · detectLoop · withTimeout
ACT 3 · 转变 4 / 4

安全：提示词 → 不是安全边界

以前我以为

在 prompt 里写上「你不许删文件、不许泄露密钥」就安全了；模型听话 = 系统安全。

现在我知道

提示词是引导，不是执法：模型可以被任何输入带偏，安全必须独立于模型意志存在——在代码里，不在话术里。

▸

四道防线，全在执行路径上：危险操作先审批（用户一键放行/拒绝）→ 敏感路径直接拦截（.env / .ssh / id_rsa）→ 输出脱敏（密钥形态打码再进上下文）→ 防循环兜底。

▸

引导与执法分离（deepseek-harness 的哲学）：上下文内容负责引导模型行为得好，独立机制负责保证它坏不到哪去——两者互不越界。

▸

最反直觉的一点：拦截时还要把原因告诉模型——它常常会自己换一条合法路径完成任务，而不是直接失败。

闸门长在执行路径上——提示词负责引导，这四道负责执法，互不越界。
文献印证 deepseek-harness 设计哲学 代码印证 beforeToolCall / afterToolCall / needsApproval
ACT 4 · 踩坑

三个真实的坑，每个都迭代了一版

坑 1
Skills 关键词匹配「看着能跑，用着漏激活」

第一版用关键词激活技能：「帮我看看这段代码有什么问题」不含「审查」二字就不生效；关键词枚举不完；指令逐轮淡出。→ 第二版改成目录常驻 + 模型语义路由 + 压缩后可重载自愈——把「理解意图」还给模型。

坑 2
abort 时压缩「半新不旧的上下文，压出坏摘要」

用户中断的瞬间如果触发压缩，拿到的摘要会污染后续所有对话。→ 立下红线：abort 不压缩；加上「压缩失败不替换原文」——空摘要比没有摘要更危险。

坑 3
压缩切在工具配对中间「恢复会话，API 直接 400」

裁剪历史时切在 tool_call 与 tool_result 之间，会话恢复直接被 API 拒绝。→ 总结切点三规则：只切消息边界、不切配对、整轮对齐——教训变成了单测。

第一版几乎总是错的——日志让每一个错都变成了资产。 三个坑没有一个是靠「想清楚」躲过的，全是跑出来、记下来、改掉的。
ACT 4 · 沉淀

三条设计哲学：学到，也被自己印证

精读 deepseek-harness 时摘出三条哲学，回头发现自己的每一次踩坑都是它们的注脚——好设计不是发明出来的，是教训的结晶。

PHILOSOPHY 1
Log 是唯一权威

一切「当前状态」都是从日志折叠出来的投影，连删除都只是投影替换，日志永不删。
我的印证：会话逐行落盘、逐行容错——崩溃后从日志重放即恢复，天然可审计。

PHILOSOPHY 2
追加优先，失效最晚

只 append + replace，不改写历史——旧数据失效得越晚，系统越稳。
我的印证：待办清单用「整表替换」维护，最新状态永远贴在上下文尾部，天然保鲜、零重注入。

PHILOSOPHY 3
引导与执法分离

上下文负责引导模型行为，独立机制负责执法保证底线，两者互不越界。
我的印证：四道防线全部长在执行路径的代码里——提示词永远不是安全边界。

来源 deepseek-harness 源码答疑 19 条 我的用法 评估任何 agent 系统时，先拿这三条照一遍
ACT 4 · 变化

学完之后，我变了

变化一用 AI 的方式

看得懂它在干什么：每轮组装上下文、调工具、回填结果——不再是黑盒魔法；它卡住时我会诊断：是超窗了？工具失败了？还是在绕圈？；知道怎么配合它：反馈给结构、确定性交给工具，而不是反复口语化地「求它」。

变化二看 AI 产品的眼光

一眼分清「套壳聊天」与「真 harness」：问它有没有循环、预算、工具契约、护栏、日志五个要素；不被 demo 唬住：演示永远顺路，问它的压缩策略、失败路径、恢复机制；评估有了框架：五要素就是我的检查清单。

▸

从「这个工具好神奇」到「这个工具在第几轮做了什么、为什么有效、边界在哪」——提问的粒度完全变了。

▸

对「AI 取代程序员」的焦虑也变了：harness 本身就是要人写的工程——理解它的人，是设计者而不是被替代者。
