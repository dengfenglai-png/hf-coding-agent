01 · 架构 — Loop 是唯一入口

一个循环，调用其余一切

参照本项目（pi-from-scratch）与 deepseek-harness 的共同骨架：系统里没有「主程序」， 只有 agent loop 这个入口——它每轮组装上下文、调用模型、分发工具、回填结果； 上下文管理、工具、护栏、生态、持久化，全部是被循环调用的模块。

↓用户需求进入循环（一句话即可）
AGENT LOOP
唯一入口 · while 循环 · 直到满足停止条件
↻
下一轮
①组装上下文

system 提示 + 工具清单 + 对话历史 → 拼成本轮请求

↓
②调用模型（流式）

LLM 返回文本增量或 tool_call（要做什么动作）

↓
③分发工具调用

过安全闸门 → 执行工具（读文件 / 跑命令 / 调 API）

↓
④回填结果 + 管预算

工具结果喂回上下文；检查 token 预算，必要时压缩 → 回到 ①

⟵ loop 每轮第④步调用
上下文管理

token 估算 → 超预算找安全切点 → 摘要压缩。上下文是有限资源，必须像预算一样经营。

⟵ loop 收到 tool_call 时调用
工具系统

每个工具有契约（名称 / 描述 / 参数 schema / 超时）；同轮多个调用并行执行。工具是模型唯一的动作形式。

⟵ loop 每轮第②步调用
LLM 适配层

流式接口以参数注入——换模型厂商，循环一行不改；失败不抛异常，编码进事件流。

⟵ loop 第③步执行前后过闸
安全护栏

危险操作先审批、敏感路径直接拦截、输出脱敏、重复调用强停——能干活的系统必须有闸门。

⟵ 工具从哪里来
生态插座

内置工具 + MCP（接外部工具服务）+ Skills（按需加载的工作流知识）——能力即插即用。

⟵ loop 每轮落账
会话持久化

逐行追加、逐行容错——崩溃后重开，从日志恢复现场接着干。

↓停止条件满足（任务完成 / 截断 / 中断 / 出错）→ 交付结果

一句话：模型负责决策，循环负责驱动，其余模块负责让决策能落地、可恢复、不闯祸。 接下来的七个问题，全部由这张图上的某个模块回答。

04 · 作答 — 来自答疑日志的一手答案

七问七答，不展示代码，只讲机制

A1
上下文超窗了怎么办？——经营它，像经营预算

先估算，再行动：按字符数近似估 token，用量到窗口的 80% 就提前动手——留出余量，绝不打满。

找安全切点：从旧消息开始移除，但切点必须是完整消息边界、绝不能切在工具调用与结果的中间（切错一处，下次请求直接被 API 拒绝）。

摘要压缩：让模型自己把旧对话总结成一条摘要，保留「系统提示 + 摘要 + 最近对话」继续干活。

两条压缩红线：压缩失败时保留原文（空摘要比没有摘要更危险）；用户中断的瞬间不压缩（半新不旧的上下文最容易压出坏摘要）。

生产级做法（深读补充）：deepseek-harness 先剪枝再压缩（超长工具结果只留头尾）；压缩从最早可压缩区开始、保留尾部比例；摘要请求本身复用前缀缓存；摘要不比原文短就拒绝压缩。
A2
只会生成文本的模型，怎么「动手」？——工具调用闭环

关键机制：模型输出里可以携带结构化的「工具调用」（调哪个工具、什么参数）——这是它唯一的动作形式，文本不是动作。

每个工具是一份契约：名称 + 用途描述 + 参数 schema + 超时。harness 负责校验、执行、把结果作为「感知」喂回上下文——模型看完结果决定下一步。

这就构成了闭环：决策（模型）→ 行动（工具）→ 感知（结果回填）→ 再决策。学术界叫 ReAct，工程上就是 loop 的第②③④步。

确定性交给代码：排序、统计、解析这类活让工具里的代码去干——模型只做路由，不做算术。

A3
参数传错、工具失败、原地绕圈——怎么收场？

错误是给模型看的，不是给人看的：参数校验失败返回结构化错误（哪个字段、什么问题）——模型读到后自己纠正重试，多数错误在循环内消化。

失败不炸循环：工具错误、网络错误一律编码进事件流，循环永不因异常崩溃；对限流和服务器错误做指数退避重试。

超时兜底：每个工具声明时限（读文件 10 秒、搜索 15 秒），到点把结果替换成超时错误——不让一个卡死的工具卡死整个 agent。

绕圈检测：连续多次调用完全相同的工具 + 相同参数 = 死循环特征，强制停下交还控制权。

A4
删库、泄密钥怎么防？——四道防线，闸门在执行前

第一道：事前审批——删除文件、执行危险命令这类工具标记为「需审批」，执行前先问用户，一键放行或拒绝。

第二道：通用拦截——不管模型怎么包装请求，触碰敏感路径（环境变量文件、SSH 密钥等）直接阻止，并告知原因。

第三道：事后脱敏——工具结果里的密钥形态文本自动打码，再进入上下文。

第四道：防循环——与 A3 共用的绕圈检测，从行为层面兜底。

深读补充：deepseek-harness 把这条总结为「引导与执法分离」——模型行为靠上下文内容引导，安全靠独立机制执法，两者互不越界：提示词永远不是安全边界。

A5
崩了、中断了，重开还能接着干吗？——日志即真相

会话逐行落盘：每条消息追加写日志——崩溃可能写出半行 JSON，恢复时跳过损坏行而不是丢弃全部历史。

配对安全（核心红线）：API 要求每个工具调用必须有对应结果。用户中断时丢弃未完成的调用，并为被跳过的调用补上错误结果——保证任何时刻的会话都是合法的，恢复后不会报错。

重开 = 重放：不存「内存状态」，恢复就是从日志重建上下文——单一真相，天然可审计。

深读补充：deepseek-harness 把这点做成制度——日志是唯一权威，所有「当前状态」都是从日志折叠出来的投影；连「删除」都只是投影替换，日志永不删。

A6
接新工具、加技能、换模型——要改核心吗？——不用，一行不改

外部工具走 MCP 协议：启动子进程、握手、发现工具清单、按需调用——外部服务的工具被适配成普通工具，循环根本不知道它来自哪里；某个服务连不上只警告，不阻塞启动。

技能（Skills）按需加载：技能目录（名字 + 一句话描述）常驻系统提示；模型判断任务匹配后，再用「加载技能」工具取出完整指令——不匹配的技能一个字都不占上下文。

换模型靠接口注入：模型调用以参数形式传入（OpenAI 兼容 / Anthropic 双后端）——切换厂商，agent 核心一行不改。

架构保证：核心层不认识任何具体工具，全部依赖由拼装层注入——扩展是「加」，不是「改」。

A7
干到一半，模型忘了最初的指令怎么办？——常驻 + 自愈

我踩过的坑（答疑日志原案）：第一版技能用关键词激活——「帮我看看这段代码有什么问题」不含「审查」两个字就不生效；关键词枚举不完；而且只在当轮生效，下一轮指令就淡出了。

改版方案：目录常驻 + 模型自己判断何时加载；加载出的完整指令留在对话历史里，后续轮次天然可见，无需重载。

压缩后自愈：即使摘要把指令压丢了，目录还在系统提示里——模型可以随时重新加载，不依赖任何内存状态。

任务进度同理：待办清单用「整表替换」式工具维护——最新清单永远贴在上下文尾部，天然保鲜、零重注入。

七个问题，一个答案：把「一次文本生成」包进「循环 + 上下文管理 + 工具 + 护栏 + 生态 + 日志」， 模型就从聊天框变成了能交付项目的 agent。 以上机制全部出自本项目答疑日志（问题 + 方案 + 取舍），并与 pi / deepseek-harness 生产实现交叉验证。
