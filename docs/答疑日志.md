## P1-1a token 估算

### 问题

`agent.ts` 的 `compactContext` 用消息条数（`COMPACT_THRESHOLD = 50`）判断"上下文是否快满"，但一条消息可能是 3 个字也可能是 3000 字，条数无法反映真实占用，导致压缩时机不准。

### 参考实现

分析 deepseek-harness 的 `packages/llm/token-meter/src/estimate.ts`：
- 固定密度启发式 `CHARS_PER_TOKEN = 4`（英文经验值：1 token ≈ 4 字符）
- 结构开销 `BLOCK_OVERHEAD = 4`（每个 block）、`ROLE_OVERHEAD = 4`（每条消息 role 字段）
- 递归按 block 类型估算（text / tool-call / tool-result / 未知）

orca 是编排器，无 token 估算实现（token 交给各 agent）。

### 方案

新建 `src/context-management.ts`，实现 token 估算 + 压缩阈值推导。

**关键决策与理由：**

1. **系数 `CHARS_PER_TOKEN = 2`（不照搬 deepseek 的 `/4`）**：`/4` 是英文启发式，而 pi 以中文对话为主。中文 1 字 ≈ 1~2 token，用 `/4` 会低估约 4 倍，对"防爆上下文"危险（估少了 → 以为没满 → 继续加消息 → 撞上模型上限 → API 报错）。折中取 `/2`，安全优先（高估比低估安全）。
2. **加结构开销** `ROLE_OVERHEAD=4` + `BLOCK_OVERHEAD=4`：贴近真实，方便对照 deepseek 扩展。
3. **阈值从 `Model.contextWindow` 推导**（新增字段，默认 128K）：`contextWindow − maxTokens − 安全余量`，不写死魔法数字。
4. **独立文件** `context-management.ts`：未来 P1-1b（切分点）、P1-1c（摘要校验）都放这里。

### 代码落点

| 文件 | 改动 |
|------|------|
| `src/context-management.ts` | 新建：`estimateContentTokens` / `estimateMessageTokens` / `estimateContextTokens` / `compactTriggerTokens` |
| `src/llm.ts` | `Model` 类型加 `contextWindow?: number` |
| `src/agent.ts` | `compactContext` 把条数判断换成 token 判断 |
| `test/context-management.test.ts` | 新建：估算函数测试 |

---

### Token 化原理（复习）

- token 是 BPE 分词器切出的"子词单元"，不是字符。
- **英文**：1 token ≈ 4 字符（OpenAI 官方经验值），字符多、token 少。
- **中文**：1 字 ≈ 1~2 token（常见字 1 token，生僻字可能 2），字符少、token 多。
- 所以中文 token 密度远高于英文，统一系数必然对某一边不准；`/2` 是折中。

## P1-1b cut point 边界

### 问题

`compactContext` 用 `slice(0, -KEEP_RECENT)` 直接按条数砍，两个隐患：
1. 切点可能落在 tool_use/tool_result 配对中间，产生孤儿 tool_result → session 恢复后 API 报 400。
2. "保留 N 条"仍是条数，与 1a 的 token 化不配套。

### 参考实现

deepseek-harness `compaction-basic/region.ts` 的 `selectCompactableRange` + `compaction/tool-pairing.ts`：
- 从尾部累加 token 凑够保留预算 → 候选切点
- 维护 in-progress tool call 计数（tool-call +1 / tool-result -1），计数为 0 的位置才可切

### 方案

`context-management.ts` 新增：
- `KEEP_RECENT_TOKENS = 4000`（保留预算，约 128K 的 3%）
- `toolPairBalance(messages)`：消息级平衡计数（assistant 的 tool_use block +N，user 的 tool_result block -N）
- `findCompactCut(messages, keepTokens)`：从尾部累加 token 凑预算 → 往前退到 balance===0 的切点；退到 0 表示放弃压缩

`agent.ts` 的 `compactContext` 改用 `findCompactCut` 替代 `slice`。

## P1-1c 摘要安全校验

### 问题

`compactContext` 压缩后无条件替换 context，但如果 LLM 生成的摘要比原文还长，压缩反而更占空间。现有代码只处理了"摘要为空"（`if (failed || !summary) return`），没处理"摘要不比原文小"。

### 参考实现

deepseek-harness `region.ts` 的 `summarizeCompaction`：用 `estimateMessage` 估算摘要 token，与 shadowedTokenCount 比较，`>=` 就拒绝（`summary is not smaller than the shadowed content`）。

### 方案

`context-management.ts` 新增纯函数 `isSummaryWorthCompacting(summary, oldMessages)`：估算摘要消息 token 与被压缩内容 token，摘要必须**严格小于**原文才返回 true（用 `>=` 拒绝，与 deepseek 一致）。

`agent.ts` 的 `compactContext` 在校验失败时 `return`（保留原文、不压缩，等下一轮）。

## P2-1 args 校验

### 问题

`agent.ts` 执行工具时把 `tc.args` 直接传给 `execute`，无校验（代码注释承认"生产应先 validate"）。模型传错参数类型（如 path 传数字）会导致工具内部报错不清晰。

### 参考实现

deepseek-harness `tools/schema.ts`：工具定义带 JSON Schema 的 parameters，`validateArgs` 执行前校验返回 violations 数组，违规抛 `ToolArgsError`（不执行工具体，返回给模型重新生成）。

### 方案

`tools.ts` 新增 `validateArgs(schema, args): string[]`（手写轻量校验，支持 object + string/number/boolean + required，零依赖）。

`agent.ts` 执行工具前校验，违规时把 `error: invalid arguments: ...` 作为 result 返回给模型（与"未知工具"处理一致），不执行工具体。

## P2-2 并行执行（安全/独占）

### 问题

`agent.ts` 用 `for...of` 严格串行执行工具，即使互不依赖也一个个等。

### 参考实现

deepseek-harness `agent-loop/tool-calls.ts`：每个工具声明 executionMode（parallel/exclusive），maxParallelToolCalls 限并发，结果 model-ordered。

### 方案

`AgentTool` 加 `exclusive?: boolean`（独占标记，默认 false = 并发安全）。

- tools.ts 标记：read_file 并发安全，write_file/edit/run_bash 独占（`exclusive: true`）
- `groupToolCalls`（纯函数）：按独占工具切分组，连续非独占 = 并行组，独占 = 单独组
- `executeToolCalls`：组内 Promise.all 并行（MAX_PARALLEL=4 chunk 限流），组间串行
- abort 语义简化：每个工具执行前检查 signal，已 abort 返回 'error: aborted'（删掉原"补结果"循环）

## P2-3b 危险命令检测

### 问题

### 方案

`tools.ts` 加 `isDangerousCommand(command): boolean`，用正则数组匹配"命令 + 高危标志"（非命令名本身）：

- `sudo`、`mkfs`、`dd`、`shutdown`/`reboot`/`halt`

`run_bash` 加 `needsApproval`，防御性检查 `command` 是 string 后再匹配。

## P3 重试退避

### 问题

LLM 调用失败（网络抖动、429 限流、5xx）无重试，直接报错。

### 参考实现

pi `ai/src/utils/retry.ts` + `provider-retry.ts`：两层重试（provider 层按状态码、assistant 层按错误消息），核心原则：指数退避（`baseDelayMs * 2^(attempt-1)`）、有界（maxRetries）、abort 终态、分类 fail-fast（配额/账单不重试）。

### 方案

`llm.ts` 加：
- `RetrySettings` 类型（enabled / maxRetries=3 / baseDelayMs=2000，参考 pi）+ `Model.retry` 字段
- `isRetryableStatus`（429 + 5xx）、`isNonRetryableError`（配额正则，因配额错误可能伪装成 429）
- `retryableFetch`：429/5xx/网络错误退避重试，配额 fail fast，abort 中断
- `stream` 的 fetch 换成 `retryableFetch`

## Skills 机制（指令 + 工具 · 关键词自动匹配 · 代码注册）

### 问题

agent 的工具来源只有内置工具 + MCP，能力扩展方式单一；缺少「打包一组指令 + 工具」的可插拔单元（对应 P5 生态扩展的插件工具）。

### 参考实现

- pi `agent/src/skills/skill.ts`：skill **纯指令**（SKILL.md + name/description），**无工具**、不注册 keyword trigger，靠 LLM 语义路由 + `/skill:name` 显式调用，渐进披露（system prompt 只放 name+description 列表，正文模型用 read 工具按需读）
- deepseek-harness `SkillRegistry`：SkillDefinition（name/description/content）+ SkillSummary 目录，三阶段「目录 → 摘要 → 按需加载」，invocation policy 区分 modelInvocable / userInvocable

两者均**不把工具塞进 skill**、均**不靠关键词触发**（LLM 语义路由 + 显式命令）。

### 方案（用户决策：指令+工具 / 关键词自动匹配 / 代码注册）

新建 `src/skills.ts`（纯函数，零依赖）：

- `Skill = { name, description, trigger[], prompt?, tools? }` —— 指令片段 + 可选 AgentTool 打包
- `matchSkills`（trigger 大小写不敏感子串匹配，命中多个全返回，保持注册顺序）
- `buildSkillPrompt`（激活的 prompt 拼成 `<skill:name>` 片段追加到 system prompt）
- `collectSkillTools`（汇总激活 skill 的工具，同名去重保留先注册的）
- `builtinSkills()` 代码注册两个教学示例：**code-review**（带 review_file 启发式检查工具，演示「指令+工具」）、**react-style**（纯指令无工具，演示「纯指令 skill」）

cli.ts 每轮 `runAgent` 前：`context.systemPrompt = SYSTEM_PROMPT + buildSkillPrompt(active)`、`tools = [...builtinTools(), ...mcpTools, ...collectSkillTools(active)]`，激活时打印 `[skills] name`。**agent 核心一行不改**（runAgent 每轮重读 systemPrompt 与 tools）。

**取舍：**
1. 参照实现均「纯指令 + LLM 语义路由 + 渐进披露」，本实现按用户决策简化为「关键词匹配 + skill 内联工具」——牺牲灵活性换确定性与可教性
2. **逐轮激活**：本轮命中即本轮生效，下一轮重新匹配（无会话级状态）；代价是后续轮次不命中关键词则 skill 指令淡出
3. 同名工具语义：skill 工具加在 builtin+mcp 之后，runAgent 内 Map 后写覆盖（skill 工具覆盖内置）

## Skills 激活方式改版（目录 + load_skill 模型自主路由）

### 问题

关键词匹配的局限：
1. **字面匹配**：「帮我看看这段代码有什么问题」不含「审查/review」→ skill 不激活；换种说法就漏
2. **trigger 列表人工维护**：枚举不完用户的表达方式
3. **逐轮激活导致指令淡出**：多轮任务里后续轮次不命中关键词，skill 指令就消失

### 参考实现

deepseek `packages/skill/tool-skill/src/index.ts`：
- 目录渲染成 `<available_skills>` 块（name + description 摘要）注入上下文，配引导语「任务明确匹配某个 skill 的描述时，先用 skill 工具加载完整指令再行动；目录只有摘要，未加载前不要推断 skill 的指令」（防从一句话摘要幻觉指令）
- 模型侧加载工具就叫 `skill`（参数 name），返回 `<skill_content>` 包裹的完整指令
- 三阶段渐进披露：目录常驻（少量 token）→ 模型自主判断 → 按需加载正文（用到才进上下文）

### 方案

`src/skills.ts` 改版：
- `Skill = { name, description, prompt, tools? }`——删 `trigger`，`prompt` 改必填
- 删 `matchSkills` / `buildSkillPrompt`，新增：
  - `buildSkillCatalog(skills)`：生成 `<available_skills>` 目录 + load_skill 使用引导，追加到 system prompt
  - `createLoadSkillTool(skills)`：`load_skill` 工具，参数 `{ name }`，返回 `<skill_content>` 包裹的完整指令；未知名字报错并列出可用名（模型可自我纠正）
- skill 自带工具**常驻注册**（不随加载动态挂载）——按需改工具列表要动 agent.ts 的工具快照，不值得；工具描述本身已说明用途，skill 指令补充工作流

cli.ts 接入（比关键词版更简单，回到启动时一次）：
- `context.systemPrompt = SYSTEM_PROMPT + buildSkillCatalog(skills)`
- `tools = [...builtinTools(), ...mcpTools, ...collectSkillTools(skills), loadSkillTool]`
- 删掉每轮 matchSkills 块

**对比关键词版的收益：** 语义路由不怕换说法；加载结果留在 messages 里，**后续轮次无需重载**（关键词版每轮淡出是缺陷）；压缩后摘要丢了指令，模型可重新 load_skill（自愈）。

**取舍：**
1. 激活多一次工具调用往返（模型先 load 再干活）
2. 依赖模型判断力——弱模型可能漏激活或过度激活；关键词版是确定性的
3. 目录每轮占少量 token（一句话/skill，可忽略）

# deepseek-harness 架构答疑汇总

> 2026-08 会话中围绕 deepseek-harness 源码的系列提问与答案的简明总结。每条：问题 + 要点。复习时先看要点，需要细节再回去翻源码。

---

## 1. Skills 机制怎么加载

- 三包分工的 capability seam：`dsh-skill`（SkillRegistry，ctx.skills）/ `dsh-skill-filesystem`（本地文件 provider）/ `dsh-tool-skill`（模型侧消费者）。
- 发现与加载分离：发现只解析 frontmatter（name + description）生成目录摘要；`get()` 每次重读文件拿正文——正文改动无需缓存失效协议。
- 根目录按 rank 优先级合并：project-dsh(100) > project-agents(200) > custom(300) > user-dsh(400) > user-agents(500)；同名由 scope 层级 + rank 决胜。
- 渐进披露：目录（name+description，截断 500 字符）常驻上下文，正文靠 `skill` 工具按需加载，渲染成 `<skill_content>` 规范形态。

## 2. 怎么根据用户输入匹配 skills

- 没有传统"匹配算法"：目录注入后，**由 LLM 语义判断**该不该调 `skill` 工具——模型就是路由器。
- 唯一确定性通道是 `/name` 手势：正则 `/(^|\s)\/([a-z0-9]+(-[a-z0-9]+)*)(?=\s|$)/g` 扫描**用户本人**的消息（注入内容不可伪造手势），命中用户可调用 skill 就直接注入指令。
- 目录引导语明确"目录只有摘要，未加载前不要推断指令"——防从一句话摘要幻觉指令。

## 3. description 是否每次用户输入都加载进上下文

- 不是。目录只在**首个 pre-step 注入一次**，作为带来源标记的 user message 持久进 log。
- 之后每步用 sha256 digest 对比当前目录与 log 中已发布的目录：相同 → 什么都不发；不同 → **追加**一条"替换目录"消息（不改写旧消息，保缓存前缀）。

## 4. 上下文很长时，第一次注入的目录会受影响吗

- 目录消息在 surface 上，早晚会进压缩区。自愈机制：`catalogHistory` 每步扫 log，若最新目录消息已不在 surface.nodes 里 → 重新发布替换目录。
- digest 相同的重复发布会被去重，所以自愈通常零成本（内容没变就不重发）。

## 5. Compaction 的具体实现

- 三个触发：压力（tokenMeter 超阈值 0.8×contextWindow，挂 agent/pre-step）/ 溢出（CONTEXT_WINDOW_EXCEEDED，挂 agent/request-error，返 `{kind:'retry'}` 重试）/ 手动（runMaintenance，仅 idle）。
- 管线：先剪枝（prune）→ 重测 → 仍超则压缩（compactRegion 循环）。
- 选区：头锚定（从最早可压缩消息开始），保留尾部 retainRatio；tool-call/result 必须配对完整（in-progress 计数为 0 的边界才可切）。
- 事务：compaction/start → summary → 用 surfaceOp replace 替换选中区 → end。log 只追加，"删除"是 surface 投影。
- 摘要调用逐字重放会话自己的 system prompt + tools + 被压缩区消息，只追加压缩指令——**复用 provider 暖前缀缓存**；摘要 token >= 原文则拒绝压缩。

## 6. 剪枝（tool result pruning）细节

- 针对超长工具结果：8192 code points 阈值内不动的；超出则保留头 4096 + 尾 1024，中间换成 PRUNE_MARKER。
- 为什么头尾都留：头部通常是最相关的输出（错误信息、文件开头），尾部是状态/退出码。
- 剪枝走 shadow-price 协议：发 `compaction/prune` 事件记录"如果真剪了省多少"，真剪需要独立确认——账目与动作分离。

## 7. Session 级替换：surface 与 events 的关系

- 事件溯源：log 是 append-only 不可变真相（deepFreeze，seq = 下标）；surface 是确定性 fold 出来的"当前可见消息投影"。
- surfaceOp 只有两种：`append`（新消息可见）和 `{op:'replace', start, end}`（把 seq 范围替换成一条新消息，如摘要/checkpoint）。
- 替换有严格校验（assertProvenance / replacementRange）：保证 tool 配对不悬空、replaceGeneration 失效派生缓存。

## 8. Session 机制全貌

- 事件类型合并扩展（SessionEventMap declaration merging），`ignorable: true` 前向兼容标记，SESSION_FORMAT_VERSION=0。
- append 管线：验证 → surface 预检 → push → fire-and-forget 事件；`session/flush` 是持久化屏障。
- 生命周期 prepare → enter → announce；fork 在 open turn 上拒绝；header（parentSession、seedLength 等）在 log 外。
- 派生视图：deriveMessages（带 replace 失效缓存）、requestHeader()/requestContext() 增量 fold——**所有"当前状态"都是 fold，没有第二份真相**。

## 9. Agent-loop（turn/step 生命周期）

- 核心纲领："Every request is derived from the session log"——驱动器不存对话状态，每步从 deriveMessages() 现算。
- 输入四入口：followup（next-turn 队列，唤醒）/ steer（next-step，唤醒）/ inject（next-step，**不唤醒**——注入只搭车不开车）/ cancel。
- 三态 phase：idle / maintenance / running；wakeRequested 闩锁防止维护期间丢唤醒。
- turn 循环：turn/start → preStep（inbox.claim + systemPrompt 组装 + waterfall，插件可 reject 或改写消息）→ user/message 在 step 括号内落账（log 记录模型实际看到的）→ step/end、turn/end 永远在 finally（边界必闭合）。
- buildRequest：request/header 只在 initial/resume/change 时记录（headerEquals 去重）；流式 chunk 逐条入 log 但只有 assistant/message 上 surface，sourceEventSeqs 指回 chunks。
- 工具调度：exclusive 成屏障、parallel 进有界池；**执行可乱序、提交必须模型顺序**（commitReady 只沿连续前缀推进）；abort 给未启动调用补合成错误结果，保 tool 配对完整。

## 10. KV cache 机制

- 本项目**不实现**缓存（缓存在 provider 侧），实现的是**前缀稳定性纪律**：每步请求 = 上一步前缀（不许动）+ 新后缀（只许追加）。
- 制度化：每个包 README 必须有 Model Experience（What the model sees / Token effect / KV Cache effect）三段，脚本强制；四分类：append-only / stable prefix / replacement / independent request。
- 关键机制：系统提示 section 化 + 固定 order；工具 schema 稳定（plan 模式不装卸工具正是为此）；request/header 去重；skill 目录追加式替换；compaction 是唯一替换——失效点推到最晚（头锚定），摘要调用自己重放前缀吃缓存。

## 11. Plan 机制

- 状态不是内存布尔，是 log 事件 `plan/mode {active}`（log-only、不上 surface、last-wins fold）——resume/fork/压缩免费恢复。
- 两阶段提交：空闲时 set() 立即落账；开轮期间只存 pendingIntents，等**下一个被接受的 pre-step** 才写——保证"request/header 之前的 fold = 该请求实际用的模式"（commit-at-consumption）。
- 模型感知恰好两通道：`plan:policy` 系统提示 section（order 50，常驻规则）+ 一条一次性切换通知（幂等：仅当上个 header 描述另一模式才注入）。
- `exit_plan_mode` 常注册（schema 稳定，非 plan 模式调用报错）；批准只是登记 pending，真正退出在下一 pre-step 落账——本批剩余工具调用仍在 plan 引导下。
- plan 是软引导：sandbox/approval 独立执法，互不读写。

## 12. 进入 plan 模式后 context 怎么变

- **之前的消息一字不变**（顺序、字节全同）；plan/mode 事件 log-only 不进消息历史。
- 变化只有两处，都发生在下一次请求：①系统提示 order 50 处长出一段引导文本；②尾部追加一条切换通知（一次性）。
- 缓存从 order 50 起失效是**算力账单**，不是内容变化——模型看到的历史与上一轮逐字节相同。
- 引导放系统提示而非消息：消息会被压缩总结掉，section 每次请求现算、永不被压缩——权威性 > 缓存代价。

## 13. 进入 plan 后，什么机制引导模型按计划一步步走

- **没有计划执行监督器**。运行时是 context 的策展人，不是监工——引导 = context 内容本身。
- 四阶段接力：规划期靠常驻 section（"explore and design, present via exit_plan_mode"每步都在）→ 交接点两个载荷进 context（计划全文 = exit_plan_mode 的 tool call 参数——**模型自己写的**；执行指令 = 批准的工具结果"carry out the plan"）→ 执行期 section 消失，引导 = 历史里的计划全文 + 执行指令，每步只是"计划不动 + 新结果追加" → 长程被压缩稀释后由 todo_write 兜底。
- todo_write 的设计奥义：**整表替换**（无增量更新）⇒ 最新清单永远是最后一次 tool call 的参数，天然贴尾部——尾部是压缩保留区 + 追加区，所以清单"永远新鲜、永在窗口"，零重注入机制；进度纪律写在工具描述里（也是 context）。

## 14. 记忆机制怎么设计

- 没有叫 memory 的包；记忆 = 多个生命周期上的"存放地 + 回放路径 + 压缩生存策略"，统一受 model-visible ⟺ logged 约束——所有记忆机制都是"往 log 写的人"或"从 log fold 的人"。
- 分层：情景记忆 = session log（唯一权威，append-only，resume 是重放不是恢复）；整固 = compaction（损失在 surface 不在 log）；声明性 = AGENTS.md 链（agent-instructions：首个 pre-step 注入为持久 user message，SHA-1 去重，文件变更靠观察第一方 read/write/edit 触及驱动追加通知——无 watcher）；程序性 = skills（目录常驻、正文按需，"总是相关的才配常驻"）；跨会话 = session-reference（@提及 → 冻结只读快照注入，引用即冻结、不可信即不执行）。
- 刻意没有：向量检索（用寻址：名字/路径/@提及）、自动笔记（记忆要么是 log、要么是人写的文件、要么是冻结引用——可信×可寻址×可审计）。

## 贯穿全部答疑的三条设计哲学

1. **Log 唯一权威，万物皆其写入者/折叠者**——skills 目录、plan 状态、todo、记忆全是同一模式：真相在 log，视图是 fold，内存只放"尚未取得写入资格的 pending"。
2. **引导与执法分离**——模型行为靠 context 内容引导（section/消息/工具描述），安全靠 sandbox/approval 独立执法；运行时不做"纠正意图"的事。
3. **追加优先，失效最晚**——所有机制尽量 append-only；必须改前缀时（compaction、plan 切换）把失效点推到最晚、并让引发替换的调用自己复用失效点之前的缓存。

## 15. Subagent 机制

- **子 agent 不是一个新引擎，就是一个普通 Agent + Session**——seam 几乎不写"执行代码"，只写"编排代码"。孩子需要的每个能力都复用既有原语：血统=`parentSession`+`delegationDepth`；fork 继承=`CreateAgentOptions.seed`（和 resume 同一个 primitive）；排队=Agent inbox 唯一 FIFO；冷恢复=`ctx.agents.resume()`（不经过 provider）；并行=loop 滚动池。
- **两种生命周期**：one-shot（函数调用，`SubagentRun` 用完即弃，父等 `run.result`）vs continuable（常驻 worker，持久 child Session + 进程内 Activation，父拿 childId 不等）。
- **Activation 三态从现有事实推导**（running/waiting/settled），不维护第二个状态机；"逻辑存在 ≠ 进程内驻留"是跨重启的关键。
- **归属是记录，权力是事实**：MessageSource 记录"谁说的"，授权核对活对象关系；"孩子说的话 / 运行时报告的孩子结局 / 父的指令"是三种不同 kind，转录不张冠李戴。
- **护栏**：深度上限（maxDepth 默认 3，到顶工具仍可见、调用报错——不藏工具）；toolFilter 是配置不是权威天花板（security 是 non-goal）。

## 16. Spill / Storage / Terminal / Workflow / Workspace 五子系统

- 归类：spill/terminal/workflow 是三个 capability seam（模型能用）；storage/workspace 是两个 host-side 数据层（模型完全看不到）。
- **Spill**：完整工具输出落盘（spill file），上下文只放有界 head/tail 预览 + locator。分层干净：output-retention 管"留了什么"、spill-policy 管"何时 spill"、spillStore 管"存哪"。spill 失败 best-effort 绝不把成功调用变成 isError；`truncated` 是预算事实≠上游不完整。
- **Storage**：非 session 数据的 hub，三层——backend 管介质（json/sqlite 并行）、domain 管语义（zod 校验）、hub 只做注册表不碰 IO。消费者走 data form 不摸 backend；写入顺序：先落盘→再改内存→再发事件。
- **Terminal**：持久 PTY，和一次性 bash 互补。精确 Agent 所有权（偷到 id 也访问不了）；六个工具；send 后台复用 ctx.jobs；引导语明确"仅需持久状态/交互 stdin 才用"。
- **Workflow**：模型写编排脚本、引擎执行、fan-out subagent。`run.result` 永不 reject（失败 resolve 成 stopReason）；WorkflowError 带 fatal 标志——致命错穿透 parallel/pipeline，普通子失败 agent() 返回 null 给脚本兜。安全上限（AGENT_CAP/ITEM_CAP）对脚本不可见。
- **Workspace**：host-side 实体注册表，用 domain 存储持久化。按 canonical path 去重；顺序持久（DOM-insertBefore 式）；delete 只删注册记录、绝不动目录/文件/会话；启动 bootstrap 只读 header 不读正文。

## 17. Workflow 具体例子（并行审计+汇总）

- 工具调用三参数职责分：`meta`=身份与进度词汇、`script`=纯 JS 控制流、`args`=纯数据（防注入）。
- 脚本钩子：`agent()`（fan-out 子 agent，带 schema 强制结构化输出、无需 parse）、`parallel()`（屏障）、`pipeline()`（无屏障流水线）、`phase()`（仅进度词汇，不构成执行结构）、`log()`、`budget`。
- 引擎：start() 同步校验（meta/语法/provider/上限，错了 reject 无 run）→ worker-thread 隔离执行 → 普通子失败 agent() 返 null（脚本 filter 兜）→ 致命错穿透 → 脚本 return 值序列化校验成 result.value。
- 父只见三样：完成提示 + agent 数 + 截断保护的 JSON 返回值；中间子 agent 消息一条不进父上下文。

## 18. Subagent vs Workflow 区别

- **不是"能不能并行"**：模型一轮消息里本来就能并行发多个 subagent 工具调用。
- 真正分水岭 = **编排逻辑住在哪**：subagent 的编排在模型脑子里、散在多轮对话（隐式、逐轮、不可复用）；workflow 的编排被写成一段脚本（显式、确定性、可复用）。
- 关系：workflow 的 `agent()` 钩子底层走的就是 subagent seam——**workflow 是 subagent 的上层**，不是替代品。
- 心智模型：subagent=老板一个个打电话；workflow=老板写方案书交给项目经理照章执行。
- 何时用：1~2 个委托用 subagent；明确大规模编排才用 workflow（写死在工具提示里）。

## 19. 为什么都做成 tool

- **被迫**：模型唯一的动作形式就是 tool call，文本不是动作——任何让模型"能做"的能力只能是 tool。
- **划算**：tool 机制自带 schema 校验、结果信封、日志（model-visible⟺logged）、并发调度、作用域、provider 绑定，全部免费继承。
- **哲学一致**：模型是路由器、工具是手——判断力留在模型（它擅长且会进化），机制做成工具（稳定、需记账）；loop 保持最小（只 turn/step 生命周期+流式+工具调度），能力全部插件化。
- 被弃方案：焊进 loop（违背"plugins not loop changes"，loop 变成知道具体能力的 spine）；单独编排运行时（造第二套控制面，重造校验/结果/日志）。
- 边界：模型能"主动决定做"→tool；"被动拥有"→context（section/注入）；"完全不参与"→基础设施（session/storage/workspace）。

# 可用性改造：给个 key 就能用的 TUI harness（P3-2 / P3-3 / P4-1 / P4-2）

> 目标：把教学版做成"提供 API key 即可日常使用"的 TUI harness 工具。按 5 小步推进，每步独立可验。

## P3-2a 启动守卫修复 + bin shebang

### 问题

1. `cli.ts` 的 main 守卫 `import.meta.url === \`file://${process.argv[1]}\`` 是字符串拼接：项目路径含空格时（本项目就在 `Desktop/vibe code/` 下），`import.meta.url` 把空格编码为 `%20` 而 `argv[1]` 保留原样，两串永不相等 → `main()` 不执行，进程零输出 exit 0。实测 `npm run dev`（tsx）与 `node dist/cli.js` 均复现。
2. `dist/cli.js` 无 shebang，`package.json` 的 `bin` 指向它，`npm link` / 全局安装后命令无法直接执行。

### 方案

1. 守卫改用 Node 官方 idiom：`import.meta.url === pathToFileURL(process.argv[1]).href`，同时正确处理空格、特殊字符与 Windows 路径。
2. `src/cli.ts` 首行加 `#!/usr/bin/env node`（tsc 会保留 shebang 到产物），build 时 chmod +x（node 一行实现，跨平台）。

### 代码落点

| 文件 | 改动 |
|------|------|
| `src/cli.ts` | 首行 shebang；守卫改 `pathToFileURL` |
| `package.json` | build 追加 chmod |

## P3-3a provider 预设表 + anthropic baseUrl 放开

### 问题

- 默认值不自洽：baseUrl 默认 openai、model 默认 `glm-5.2`，开箱组合必然 401/404。用户拿任何一家的 key，都必须同时知道改 provider / model / baseUrl 三个变量。
- `anthropic.ts` 写死 `ANTHROPIC_BASE_URL`，`model.baseUrl` 对 Anthropic 后端不生效，中转站用户无法使用。

### 参考实现

pi 的 provider 定义（`packages/ai/src/providers/*.ts`）：每家一个小定义对象 `{ baseUrl, auth }`，如 deepseek = `https://api.deepseek.com` + `DEEPSEEK_API_KEY`。provider id 是唯一选择器，baseUrl / 默认 model / env key 名都挂在定义里。

### 方案

新建 `src/providers.ts`（按内容命名的预设表，非 utils）：

```ts
type ProviderPreset = {
  baseUrl: string
  model: string
  protocol: 'openai' | 'anthropic'
}
```

内置 openai / anthropic / zhipu / deepseek / openrouter 等预设。`loadConfig` 的解析顺序：显式 env（`NANOPI_MODEL` / `NANOPI_BASE_URL`）> config 文件 > 所选预设的默认值。anthropic 后端改用 `model.baseUrl ?? ANTHROPIC_BASE_URL`。

### 代码落点

| 文件 | 改动 |
|------|------|
| `src/providers.ts` | 新建：预设表 + 查询函数 |
| `src/cli.ts` | loadConfig 三段解析顺序接入预设 |
| `src/anthropic.ts` | baseUrl 走 `model.baseUrl` |
| `test/cli.test.ts` | 预设解析测试 |

## P3-3b API key 三种来源（flag / config / 首次录入）

### 问题

key 只认 `NANOPI_API_KEY` 环境变量。没有 CLI flag、没有持久化录入、没有首次运行引导；401 时直接吐 raw API 错误，无"检查 key"提示。

### 方案

key 解析优先级：`--api-key` flag > `NANOPI_API_KEY` env > `~/.nanopi/config.json` 的 `apiKey` 字段。三者皆无时进入首次录入：提示输入 → 写入 config.json 并 `chmod 600`。API 返回 401/403 时提示"key 无效或无权限，请检查 NANOPI_API_KEY / --api-key"。

### 代码落点

| 文件 | 改动 |
|------|------|
| `src/cli.ts` | key 三级解析 + 首次录入 + 401 友好提示 |
| `test/cli.test.ts` | 优先级测试 |

## P4-1a 显式退出 + 基础 slash 命令

### 方案

### 代码落点

## P4-2 状态行 + 输出分隔

### 问题

agent 运行中零反馈（等 LLM、执行哪个工具、第几轮、token 用量全不可见）；`printText / printToolCall / printToolResult` 纯文本直写，中文提示与流式输出混作一团。

### 方案

克制实现（不做渲染框架）：

- 分隔：回合开始打印淡色 `─` 分隔线 + 用户输入回显；tool 调用/结果行加 ANSI 暗色；结束打印本轮耗时与 message 数。ANSI 码集中在 tui.ts 顶部常量，`NO_COLOR` 时退化为纯文本。

### 代码落点

| 文件 | 改动 |
|------|------|
| `src/tui.ts` | spinner 状态行 + ANSI 常量 + 分隔/回显 |
| `src/cli.ts` | 事件里带轮次信息喂给状态行 |
| `test/tui.test.ts` | spinner 帧与 NO_COLOR 测试 |

## P3-5 全局命令 pi-agent + 按项目目录隔离 session

### 问题

用户目标形态：像 claude 一样，cd 进任意文件夹后运行 `pi-agent` 进入 harness。当前差距：
1. bin 名是 `pi-from-scratch`，非 `pi-agent`。
2. session 是全局单文件 `~/.nanopi/session.jsonl`——在 A 项目聊的历史会混进 B 项目的上下文；工具虽按相对路径取 cwd，但对话记忆是错的。

### 参考实现

Claude Code：session 按启动目录隔离，存放在 `~/.claude/projects/<slugified-cwd>/`（如 `-Users-hefeng-Desktop-vibe-code-pi-agent`）；`claude` 默认开新会话，`-c/--continue` 续接最近一次。

### 方案

1. `package.json` 的 bin 改为 `pi-agent` → `dist/cli.js`（shebang 已有），`npm link` 后全局可用。
2. session 目录改为 `~/.nanopi/projects/<slug(cwd)>/session-<ts>.jsonl`，slug = cwd 中非字母数字串替换为 `-`（与 Claude Code 同规则）。
3. 启动语义对齐 Claude Code：默认开新会话（空 context）；`-c/--continue` 加载该目录最近修改的 session 文件；`/new` 在当前项目目录内开新文件。
4. 启动时打印两行欢迎信息（模型、cwd、命令提示），给"进入 harness"的仪式感。
5. 删除全局 `SESSION_FILE` 常量与默认参数，session 文件路径一律显式传入。

### 代码落点

| 文件 | 改动 |
|------|------|
| `package.json` | bin → `pi-agent` |
| `src/cli.ts` | `projectSessionDir` / `latestSessionFile` / `-c` 解析 / 欢迎行 |
| `test/cli.test.ts` | slug、latest、flag 测试 |

### 改名（后续）

bin 与命令名 `pi-agent` → `hf-coding-agent`（package.json bin、欢迎横幅、README 同步更新）；重新 npm link 并删除旧 bin 软链。`test/cli.test.ts` 里的 `-Users-…-pi-agent` 是路径 slug，与命令名无关。
